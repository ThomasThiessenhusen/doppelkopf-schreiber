# i18n / Mehrsprachigkeit (DE + EN) — Design

Datum: 2026-05-11
Status: Entwurf, vom Nutzer abgenommen (Brainstorming)

## Ziel

Einführung von Mehrsprachigkeit in der Bockzettel-App. Anfangs zwei Sprachen: Deutsch (Default) und Englisch. Sprache wird beim ersten Start aus der Geräteumgebung erkannt und kann in den Einstellungen manuell überschrieben werden. Doppelkopf-Fachbegriffe bleiben auch in der englischen Version deutsch; übersetzt wird der UI-Rahmen und die beschreibenden Texte um sie herum.

## Entscheidungen (Übersicht)

| Thema | Entscheidung |
|---|---|
| Sprachen | DE + EN |
| Sprachwahl | Auto aus OS + manuell überschreibbar in Settings |
| Fachbegriffe | Re, Kontra, Bock, Solo, Hochzeit, Schwarz, Doppelkopf, Fuchs, Karlchen, Schmeißen bleiben deutsch — Drumherum-Text wird übersetzt |
| Library | `i18next` + `react-i18next` + `expo-localization` |
| Übersetzungsformat | TypeScript-Module (`de.ts`, `en.ts`) — Typsicherheit via `typeof de` |
| App-Name (`expo.name`) | bleibt `Bockzettel` (Markenname, nicht übersetzt) |

## Architektur

### Library-Setup

- `i18next` und `react-i18next` als Framework
- `expo-localization` zur OS-Sprach-Erkennung
- Init in einem neuen Modul `src/presentation/i18n/`, eingehängt in `app/_layout.tsx` vor dem ersten Render

### Sprachpersistenz

- Erweiterung des `AppSettings`-Modells (`src/domain/models/appSettings.ts`) um:
  ```ts
  type LanguagePreference = 'system' | 'de' | 'en';
  language: LanguagePreference;   // Default: 'system'
  ```
- Persistenz über das vorhandene `settingsRepository` — kein neuer Speicherort
- Migration: alte gespeicherte Settings ohne `language`-Feld bekommen beim Laden `'system'` als Fallback (zentral in `appSettingsFallback` / Lade-Logik)
- Bei `'system'`: OS-Sprache wird via `expo-localization` gelesen. Bei `'de'`/`'en'`: manuelle Wahl, OS-Wechsel hat keinen Effekt

### Schichten-Regel

- `t()` wird **nur in der Presentation-Schicht** aufgerufen (Screens, Widgets)
- Domain-, Data- und Application-Schichten bleiben sprachfrei
- Falls dort heute deutsche Strings auftauchen (Error-Messages aus Stores), werden sie auf Error-Codes/Enums normiert; die Presentation übersetzt diese

## Übersetzungsdateien & Keys

### Struktur

```
src/presentation/i18n/
  index.ts            ← i18next-Init, Sprachresolver, Export i18n/t
  useTranslation.ts   ← getypte Re-Export des Hooks
  locales/
    de.ts             ← Default-Sprache (Source of Truth)
    en.ts             ← Englische Übersetzungen (typisiert gegen typeof de)
```

### Warum `.ts` statt `.json`

- Typsicherheit: `de.ts` definiert die Key-Struktur, `en.ts` muss strukturell `typeof de` erfüllen → fehlende Keys = Compile-Fehler
- Keine extra Bundler-Konfig
- Pluralregeln und Interpolations-Platzhalter inline lesbar

### Key-Schema

Genestet nach Feature (nicht flach). Beispiel `de.ts`:

```ts
export const de = {
  common: {
    cancel: 'Abbrechen',
    save: 'Speichern',
    delete: 'Löschen',
  },
  home: {
    title: 'Bockzettel',
    newSheet: 'Neuer Bockzettel',
    emptyState: 'Noch keine Spiele',
  },
  addGame: {
    title: 'Spiel eintragen',
    flags: {
      fuchsCaught: 'Fuchs gefangen',          // "Fuchs" bleibt DE
      doppelkopf: 'Doppelkopf',               // bleibt DE
      noLevelAnnounced: 'keine Stufe angesagt',
      levelAnnouncedN_one: 'Unter 90 angesagt +{{count}}',
      // weitere Plural-/count-Varianten
    },
  },
  settings: {
    title: 'Einstellungen',
    language: {
      label: 'Sprache',
      system: 'Systemsprache',
      de: 'Deutsch',
      en: 'Englisch',
    },
  },
  // ...
} as const;
```

### Pluralregeln / Interpolation

- i18next-Standard: `{{name}}` für Platzhalter, `_one`/`_other`-Suffix für Plurale (über `count`-Parameter)
- Existierende Funktionen wie `levelChipLabel(count)` werden zu `t('addGame.flags.levelAnnouncedN', { count })`

### Fachbegriffe in `en.ts`

Was deutsch bleibt: Re, Kontra, Bock, Solo, Hochzeit, Schwarz, Doppelkopf, Fuchs, Karlchen, Schmeißen.
Was übersetzt wird: `gefangen` → `caught`, `angesagt` → `announced`, `keine Stufe` → `no level`, alle UI-Rahmentexte.

### Zahlen-/Datumsformate

- Punktezahlen sind reine Integer, keine Lokalisierung nötig
- Datumsangaben (falls vorhanden): `Date.prototype.toLocaleDateString(i18n.language)` direkt im Widget

## Konsumption im Code

### Standard-Hook

```ts
import { useTranslation } from '@/presentation/i18n/useTranslation';

function HomeScreen() {
  const { t } = useTranslation();
  return <Appbar.Content title={t('home.title')} />;
}
```

### Typsicherheit der Keys

In `src/presentation/i18n/index.ts` Modul-Augmentation:

```ts
declare module 'react-i18next' {
  interface CustomTypeOptions {
    defaultNS: 'translation';
    resources: { translation: typeof de };
  }
}
```

→ `t('home.titel')` (Tippfehler) wird vom TS-Compiler abgelehnt. Autocomplete für verfügbare Keys.

### Outside-React-Konsumption

Falls außerhalb von Komponenten übersetzt werden muss: direkter `i18next.t(...)`-Import aus `src/presentation/i18n/index.ts`. Bleibt Ausnahme — Regel ist der Hook.

### Sprachumschaltung zur Laufzeit

`react-i18next` re-rendert alle Konsumenten automatisch bei `i18n.changeLanguage(...)`. Kein manuelles State-Management nötig.

### Error-Übersetzung aus tieferen Schichten

Wo Stores heute Fehler-Strings produzieren (`asyncError(e)`), wird der Wert auf Error-Codes normiert; das Widget übersetzt via `t('errors.<code>')`. Wo der Aufwand zu hoch ist, bleiben Roh-Fehler vorerst unverändert — wird im Implementation-Plan pragmatisch entschieden.

### Bundlegröße

Beide Sprachen werden gemeinsam gebündelt (klein, kein Lazy-Loading).

## Settings-UI & Initialisierung

### Settings-Screen

Im bestehenden `SettingsScreen.tsx` neuer Abschnitt **Sprache** mit Paper-`RadioButton.Group`:

- Systemsprache (Default)
- Deutsch
- Englisch

Auswahl → `settingsStore.setLanguage(value)` → Repository speichert → `i18n.changeLanguage(resolveLanguage(value))` → UI re-rendert.

### Store-Erweiterung

In `src/application/stores/settingsStore.ts`:

```ts
setLanguage: (lang: LanguagePreference) => Promise<void>;
```

Pattern identisch zu vorhandenem `setDefaultStackingMode`.

### Auflösungsfunktion

In `src/presentation/i18n/index.ts`:

```ts
function resolveLanguage(pref: LanguagePreference): 'de' | 'en' {
  if (pref === 'de' || pref === 'en') return pref;
  const sys = Localization.getLocales()[0]?.languageCode;
  return sys === 'de' ? 'de' : 'en';   // alles ≠ 'de' → en (Fallback)
}
```

### Init-Reihenfolge in `app/_layout.tsx`

1. SettingsStore lädt (`load()`) — bereits vorhanden
2. Sobald geladen: `i18n.init({ lng: resolveLanguage(settings.language), resources: { de, en } })`
3. Splash bleibt sichtbar bis Settings **und** i18n bereit sind → keine "Flash of Wrong Language"
4. Danach `SplashScreen.hideAsync()` und App-Render

Konkret: der vorhandene Effect, der heute auf Settings wartet, wird um i18n-Init erweitert.

### Sprachwechsel zur Laufzeit

Nur `i18n.changeLanguage(...)` — kein App-Reload. React re-rendert automatisch.

## Migration bestehender Strings

### Inventar

| Bereich | Datei(en) | Aufwand |
|---|---|---|
| Home | `HomeScreen.tsx` | klein |
| Neuer Bockzettel | `NewSheetScreen.tsx` | klein |
| Sheet-Ansicht | `SheetScreen.tsx`, `Scoreboard.tsx`, `RoundSection.tsx` | mittel |
| Spiel-Eingabe | `AddGameScreen.tsx`, `FlagChip.tsx`, `TeamPicker.tsx`, `flagSpecs.ts` | groß |
| Spieler | `PlayerManagementScreen.tsx` | klein |
| Gruppen | `GroupManagementScreen.tsx`, `GroupRankingsScreen.tsx` | mittel |
| Einstellungen | `SettingsScreen.tsx` | klein (+ Sprach-Sektion) |

### Sonderfall `flagSpecs.ts`

Heute mischt diese Datei Domain-Codes mit UI-Labels (`'Fuchs gefangen'`, `'Unter 90 angesagt +1'`). Umstellung:

- `label`-Strings raus aus den Specs → stattdessen `labelKey: 'addGame.flags.fuchsCaught'` (i18n-Schlüssel)
- `announcementChipLabel(count)` / `levelChipLabel(count)` werden in das jeweilige Widget verschoben und nutzen `t` als Closure
- Datei behält ihren Charakter als Spec, ohne Anzeige-Strings

### Was bleibt deutsch (auch in `en.ts`)

Re, Kontra, Bock, Solo, Hochzeit, Schwarz, Doppelkopf, Fuchs, Karlchen, Schmeißen — als Werte in `en.ts` genauso. Drumherum-Text wird übersetzt.

### Strings in Domain-/Application-Schicht

Stichprobenartig prüfen. Spielernamen sind User-Eingabe und werden nicht übersetzt. Error-Messages werden im Implementation-Plan einzeln behandelt (Ansatz: Error-Code statt String).

### Reihenfolge der Migration

1. i18n-Grundgerüst + Settings-Screen (mit Sprachumschalter) — minimaler vertikaler Schnitt, sofort testbar
2. Danach Screen für Screen, kleine zuerst

## Tests

- **`resolveLanguage()`**: verschiedene Inputs (`'system'` mit DE-OS → de, `'system'` mit FR-OS → en, explizite Wahl → respektiert)
- **`settingsStore.setLanguage`**: persistiert via Repository und ruft `i18n.changeLanguage` auf — analog zum vorhandenen `setDefaultStackingMode`-Pattern
- **Render-Tests** für mindestens einen Screen mit beiden Sprachen (Smoke gegen fehlende Keys)
- **Type-Check als Test**: `npm run typecheck` muss grün bleiben — fängt strukturelle Lücken in `en.ts` zur Compile-Zeit
- Bestehende Tests, die heute auf deutsche Strings prüfen, werden auf i18n-Keys umgestellt

## Nicht im Scope

- Weitere Sprachen außer DE und EN (Struktur ist aber so gewählt, dass eine dritte Sprache leicht ergänzt werden kann)
- Lazy-Loading der Übersetzungen
- RTL-Layouts
- Übersetzung von User-Eingaben (Spielernamen, Gruppennamen)
- Server-seitige Übersetzungs-Pipelines
